# Portfolio & Agency Site Template: quality report

> **Where the code is.** The measurement scripts that produced these results are part of the source package, which is distributed separately (see [SOURCE-ACCESS.md](../SOURCE-ACCESS.md)). The raw results they wrote are included in this repository under [`results/`](../results/).

Version 0.1.0 by The Diamond Empire. This report states what was measured, how, what the numbers were, and what the checks cannot tell you. Every number in the results table is generated by `npm run report:table` from files in [results/](../results/); none is typed by hand. Timing and performance scores are deliberately not measured: the machine that built this is shared and loaded, and timings from it would not mean anything.

## Verdicts

These sentences interpret the table above; the table and the files in `results/` are the source of truth.

- **Build and customer package:** the static export builds (20 documents, 19 indexable), and the ZIP, extracted into a scratch folder, installs, type-checks, lints, passes its own 226 unit tests and builds an export that is byte-identical (HTML, XML, text) to the repository build. The ZIP is byte-identical on two builds.
- **Validity:** all 20 pages are clean under the recommended `html-validate` preset with the five rule adjustments described under Limits. Against the unmodified preset the validator reports messages only from those five rules (counts in `results/html-validate.json`).
- **axe-core:** zero violations and zero "needs review" items in all 166 page loads (every page, light and dark, 320, 768 and 1280 px, forced themes, the filtered work page, the form's error and confirmation states) and no horizontal scrolling or console error in any of them. This is the result of an automated scan that finds only part of the problems that affect people; it is not a statement that the pages are free of them. (Two things that look surprising are explained under Limits and in the change log: transitions were switched off during scans, and the sample artwork contains no text.)
- **Contrast from tokens:** every checked pair passes in both themes; the smallest margin is 6.29:1 against a 4.5:1 requirement. This covers token pairs, not every pixel; axe checks rendered colours as well.
- **Weight and requests:** every page is within every budget, and no budget was changed. Pages are 10 to 17 requests and about 0.52 to 0.56 MB uncompressed (about 150 to 159 kB gzip). The JavaScript (472,070 to 479,928 bytes, 140,334 to 142,993 gzip) is within 4 percent of its 500,000-byte budget on every page, almost all of it the React and Next.js runtime, so there is little headroom: adding a client component will use it quickly.
- **Layout shift:** 0 on every one of the 40 page and width combinations, against a budget of 0.05. The control, a picture inserted without width and height, measured 0.577 in the same run, so the measurement can see a shift and the zeros mean something. This is one browser on a local server, not field data.
- **Pictures and share images:** 46 pictures on 20 pages all state whole-number width and height, have alt text and an existing file, and every SVG file's own size equals the stated one. The 19 share images are real 1200 x 630 PNG files, all different, one per indexable page, and each page's Open Graph tag points at its own.
- **Work filter:** without JavaScript every category page shows only its projects; with JavaScript a click and the Enter key filter in place (the page is not reloaded), the address, title and status text change, a click with the control key opens a new tab and leaves the page alone, and Back and Forward restore the earlier filter. The first development run of this check found a real defect (focus jumped to the main area), which is fixed.
- **Third parties:** zero requests to any other origin in the browser, no URL to another host in any page, style or feed, and no tracker pattern in any exported file. Four hosts appear only as text inside the framework runtime (error-message links).
- **Metadata, structured data, sitemap and feed:** all pages have a title, description, one h1, language and viewport, every page except the 404 has a canonical URL equal to its sitemap entry, JSON-LD parses and its addresses exist, and the sitemap, feed and exported pages agree. The 404 page deliberately has no canonical link and is marked noindex.
- **Forms:** validation, the error summary and its focus, linked error text, the marked demo confirmation and its focus, no network request on submit, double-click protection and the no-JavaScript state all pass in the built site.
- **Keyboard and motion:** on every page at 1280 and 320 px (40 walks) the Tab walk starts at the skip link, reaches every focusable element and shows a focus indicator at every stop; the skip link and a client-side page change move focus to the main area. The theme toggle follows the device theme, changes the colours and remembers the choice across a reload. With reduced motion requested, no transition or animation longer than 1 ms and no smooth scrolling on the four pages checked.
- **Licences:** 186 packages in the production tree; none is non-permissive apart from 14 optional image-library packages that npm may download and that are not used or shipped (see `THIRD-PARTY.md`). The build-time share image tool is not visible to this check; it is disclosed in `THIRD-PARTY.md`.
- **Development server:** `npm run dev` starts and answers 200 on all twelve addresses fetched (including a share image), and 404 for an unknown address.

## Limits and threats to validity

- **Automated accessibility testing finds only part of the problems that affect people.** axe-core, contrast ratios and keyboard scripts cannot judge whether alternative text is meaningful, whether the reading order makes sense, whether link text is clear, whether the wording is easy to understand, or how a page works with a screen reader, a magnifier, speech input or switch devices. No screen reader was used for this report. This report is not a statement of conformance with the Web Content Accessibility Guidelines at any level.
- **One browser engine.** The browser checks ran in one version of Chrome on Windows (headless, one viewport emulation at a time). Firefox, Safari and real phones were not tested. The work filter was tested with a mouse and the keyboard only.
- **Viewport widths 320, 768 and 1280 only.** Other widths, zoom to 200 percent and text-spacing overrides were not tested.
- **Contrast.** The contrast script checks a fixed list of token pairs. A new component with a new colour combination is not covered until its pair is added to the list. axe checks the rendered colours as well. The colours inside the generated SVG pictures and the share images are not checked: they are pictures, and their text-like shapes carry no words.
- **axe results depend on page state.** The scans ran on the loaded page, with the contact form in its error state and its confirmation state and the work page filtered. Open FAQ items and hover states were not scanned separately. CSS transitions and animations were switched off before each scan (see the change log): axe measures the colours on screen at one instant, and a colour caught half-way through a transition depends on how busy the machine is. The reduced-motion check is separate and runs on the unmodified page.
- **The in-place filter does not change the page heading.** When a visitor filters without a page load, the address, the document title and the count under the filter change, but the visible heading stays "Work"; the delivered category page (what you get on a reload or from a shared link) says "Branding work". The title and the status text carry the change; the heading was left alone on purpose to keep the enhancement small.
- **html-validate rule changes.** Next.js and React write valid HTML in a style the recommended preset does not prefer: camelCase attribute names (`charSet`, `dateTime`, `noValidate`), self-closing void tags, empty boolean attribute values (`async=""`, `hidden=""`) and one element id that starts with an underscore. The template cannot change that output, so `attr-case`, `void-style`, `attribute-boolean-style` and `attribute-empty-style` are off and `valid-id` is relaxed. The number of messages the unmodified preset would give, by rule, is in `results/html-validate.json`; a test fails if any other rule would speak. This is the validator's rule set, not the W3C Nu validator.
- **Framework weight.** Most of every page's JavaScript is the React and Next.js runtime. The template cannot remove it, so the JavaScript budget describes the framework floor plus a few small client components. The budget was set before this template was measured, using the framework floor a sibling template had measured; see the change log.
- **Page weight counts hidden projects.** The weight of a work page includes the pictures of projects that a category page hides, because their addresses are in the HTML. A browser does not fetch them (the request check records how many it did not), so the weight is an upper bound for those pages.
- **Layout shift is measured in one browser on one machine, with the site served locally.** A local server answers instantly, so a slow connection could behave differently. The measurement sums the browser's layout-shift entries until the page has been scrolled to the bottom; it does not measure shifts caused by later interaction, and it is not a Core Web Vitals field measurement.
- **Generated artwork, not photographs.** The sample pictures are small SVG files. Real photographs are larger, so a real site will weigh more than these numbers; the template's rules (stated sizes, lazy loading, optional variants) are tested, but the weight of your own pictures is not.
- **Strings inside the framework runtime.** URLs such as links in error messages appear as text inside the React and Next.js scripts. Pages never request them: the browser check records zero requests to another origin.
- **Optional image libraries.** npm may download the optional `@img/sharp-*` packages (LGPL libvips) that Next.js lists. They are unused, not in the exported site and not in the ZIP; see `THIRD-PARTY.md`.
- **Share images use a build-time tool with an MPL-2.0 licence.** The share images are drawn by `@vercel/og`, which is compiled inside `next`; its licence field is MPL-2.0, which this repository's licence check does not see (it reads the lockfile). It is not in the exported site. See `THIRD-PARTY.md`. The share images were checked for size, distinctness and presence, and looked at by eye for one page; no social network preview was fetched.
- **Sample content.** The pages contain invented clients, results, people, prices and quotes, and each page that shows results says so. The measurements describe the template, not any customer's final site.
- **Structured data** is checked for syntax, required properties and addresses that exist; no search engine validator was run.
- **The customer ZIP path** was run once on this machine with the npm cache already warm; a fresh machine may behave differently. The Next.js and npm telemetry settings were switched off with environment variables for every run.
- **Not measured:** load time, rendering performance, Lighthouse scores, Core Web Vitals in the field, real-user behaviour, search ranking. No claim about any of these is made.
- **The GitHub Actions workflow was never run.** It was written to run the same commands as local development, but this was built and verified locally only.
- **MySQL, WordPress and databases** are not involved.
- **Shared machine.** Other jobs were running during the work. This does not affect byte counts or pass/fail checks, which are deterministic, and is the reason no timings are reported.

## Change log

Disclosure of reruns and changes made after something was measured.

1. **Budgets first, none revised.** `tests/budgets.json` was written before this template's pages were measured. The JavaScript figures (500,000 bytes raw, 150,000 gzip) were chosen knowing the React and Next.js floor that a sibling template had measured (about 470 kB); that is prior knowledge, not a fit to this template's results, and it is why they are higher than a hand-written site would need. The layout-shift budget (0.05) was also fixed before the first measurement. No budget was changed afterwards.
2. **Working copies.** Installs in the synced project folder were impractically slow, so development builds and tests ran in a copy at a short path outside it, mirrored from the project folder; the source in the project folder is what was verified. The final verification used a separate fresh copy at a short path (`npm ci`, then every check there), with its outputs written outside the copy.
3. **First development run of the export tests (five failures).** (a) `html-validate` reported `no-inline-style` on every picture: the picture component set an inline `aspect-ratio`. The inline style was removed; the `width` and `height` attributes with `height: auto` in the stylesheet reserve the same space. (b) `html-validate` reported `tel-non-breaking` for the phone number, which had ordinary spaces; it now has non-breaking spaces. (c) My own sitemap test expected at least 20 URLs but there are 19 indexable pages; the test was wrong and was corrected. (d) The request check found one lazily loaded picture that had not been requested when the page was inspected; the check now scrolls in steps and waits until every visible picture has finished loading. (e) **A real defect, found by the new filter test:** the "move focus to the main area after a page change" component also fired when the filter changed the address, so a keyboard user who pressed Enter on a filter link lost their place. The component now ignores changes between the work views; a unit test and the browser test cover it. In the same run the axe-core matrix (all variants) had found no violations.
4. **Second development run (two failures).** (a) One axe-core colour-contrast result on the theme button label, in a page variant where the theme attribute is set a moment before the scan, appeared in the second development run only (it was absent from the first run and from the final measurement): the colour was probably caught half-way through a CSS transition while the machine was heavily loaded, which I did not prove. CSS transitions and animations are now switched off before each axe-core scan, and the limit is stated above; this changes what axe sees only for colours that are moving, not the final colours. (b) The wait for pictures in the layout-shift check used the browser's frame callback for polling and timed out under load; it now polls on a timer with a longer limit.
5. **Unit tests.** The contact-form tests, which type like a person, timed out at 5 seconds once under heavy load; the per-test limit for unit tests is now 20 seconds (in the repository and in the customer package). A unit test found that the check for "is this one of the work views" did not accept `/work` without a trailing slash; fixed. Type and lint fixes made along the way: a type for the MDX component map, and the React rule against changing `document.title` inside an event handler (the title is now set in an effect, and only after the visitor has used the filter).
6. **Content.** One case study showed its cover picture twice (at the top of the page and again in the text); the second use was replaced by another picture.
7. **Final run.** The code was frozen, copied to a fresh short-path folder, installed with `npm ci` and checked there (`npm run check`: type check, lint, unit and static tests; 300 tests passed, 1 skipped because the results table did not exist yet). Then `npm run measure` ran once, in one uninterrupted invocation (2026-11-09T20:27Z to 21:25Z, about 58 minutes; every check passed on that first full run), with its output written outside the copy. Afterwards `npm run test:record` recorded the whole suite from the same copy (338 tests in 23 files, 337 passed, 1 skipped, 0 failed). The outputs were then copied into `results/`, the documents were finished, and `npm test` was run once more in the same copy, with the finished documents and `results/` in place, to check that the documents, the results table and the results agree (see the line for that run at the end of this list).
8. **Changes made after the measurement, none of which changes a measured value.** (a) `scripts/report-table.mjs` was edited once: when the largest layout shift is 0 the sentence now says that all 40 combinations measured 0 instead of naming one arbitrary page. (b) The README, this report, the roadmap ticks and the phase were written after the measurement because they quote it. (c) No source, content, test or budget file was changed after the code freeze.
9. **Final check of the documents.** After the documents and `results/` were in place, `npm test` (unit and static projects) was run in the clean copy: 21 files, 301 tests passed, 0 failed, 0 skipped (the check that the results table equals what `npm run report:table` generates from `results/` ran for the first time here). It was run once more after this line was added, with the same result. The export project was not run again after the measurement: nothing it tests changed, and its recorded run is in item 7.
